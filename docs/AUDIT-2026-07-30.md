## 1. CRITICAL

### C1 — 🚨 APP_SECRET has no guard against the placeholder value ❓ Not Verified
- **Where:** `api/db.php:110,123` sign & verify every login token with `config.php`'s `APP_SECRET`. `config.example.php:21` ships the literal `'change-me-to-a-long-random-string…'`.
- **Risk:** If production `config.php` was copied from the example and the secret left unchanged, **anyone can forge a valid token for any `plant_id`** — full account takeover of every tenant. The example value is public in the repo.
- **Why unverified:** `config.php` is gitignored and lives only on the server — I can't read its actual value.
- **Fix (do regardless):** in `ql_config()` or `ql_sign_token()`, refuse to run if `APP_SECRET` is empty, shorter than 32 chars, or equal to the placeholder. ~15 min. **Verify the server's value today.**
- **Severity:** Critical if unchanged · trivial if already a real secret.

## 2. HIGH

### H1 — 🔒 No brute-force protection on login/signup ✅ Verified
- **Where:** `api/login.php`, `api/signup.php` — read in full. No attempt counter, no lockout, no delay, no CAPTCHA. The only `sleep`/`429` in the codebase are LLM-provider retries, not auth.
- **Repro:** Script 10,000 POSTs to `/api/login.php` with a fixed 10-digit phone and a password list — nothing stops it. Indian mobiles are a guessable 10-digit space.
- **Fix:** per-phone + per-IP throttle (e.g. exponential backoff after 5 fails, 15-min lockout after 10), or a `login_attempts` table. ~3–4 h.

### H2 — 🚨 No security headers (CSP, X-Frame-Options, HSTS) ✅ Verified
- **Where:** grepped all of `api/*.php` and both `.htaccess` files. Only `onboard.php:114` sets `X-Content-Type-Options`. **Nothing** sets Content-Security-Policy, X-Frame-Options, HSTS, or Referrer-Policy anywhere.
- **Risk:** The whole dashboard can be **iframed → clickjacking**. No CSP means the innerHTML-heavy rendering has zero defense-in-depth if a single `esc()` is ever missed. No HSTS.
- **Fix:** add the headers in the root `.htaccess` (LiteSpeed honors it) or a shared PHP prelude: `X-Frame-Options: DENY`, a starter CSP, `Referrer-Policy: strict-origin-when-cross-origin`, HSTS. ~2 h + CSP tuning.

### B1 — ❌ "Attendance" nav link goes to a blank page ✅ Verified
- **Where:** `shell.js:235` wires `Attendance → attendance.html`. That file is **0 bytes**. It is *not* flagged `soon` (unlike Stock/Dispatch at `:229-230`), so it renders as a live, clickable link.
- **Repro:** click **People → Attendance** → blank white page, no shell, no nav, only the browser Back button recovers.
- **Root cause:** page never built but wired as if live.
- **Fix:** one line — change to `href: SOON, soon: true` (30 sec), or build the page. Every *other* one of the 41 nav targets resolves (swept & confirmed).

## 3. MEDIUM

### M1 — 💰 Manual overpayment inflates the cashbook ✅ Verified (reproduced in source)
- **Where:** `data.js:2210-2215` (`receiveSalesPayment`) and `:1434` (`recordPurchasePayment`).
- **Bug:** the bill's `paid` is correctly capped — `paid = Math.min(total, prev + amount)` — but the very next lines push the **raw uncapped `amount`** into `S.CASHBOOK` and `s.payments[]`.
- **Repro:** ₹50,000 invoice, ₹40,000 already paid (₹10,000 outstanding). Receive Payment ₹30,000 → invoice correctly caps at ₹50,000, but the **cashbook gains a ₹30,000 credit** (₹20,000 more than the bill could absorb). Sales register and cashbook now disagree; that phantom credit can itself later be matched to a bank line.
- **Immune path:** the reconciliation "Update Payments" flow pre-caps and is safe. Only the **manual** Receive/Pay entry points (`sales.js:184`, `purchase.js:697/951`) are unguarded.
- **Fix:** `const applied = paid - prev;` use `applied` for the cashbook + payments rows (or clamp the input with a warning). Add a test asserting `cashbook.amount === applied` when `amount > outstanding`. ~1 h.
- Found by the money sub-audit, verified by me directly.

### M2 — 🔄 Two tabs/devices = last-write-wins, silent data loss ✅ Verified
- **Where:** `data.js:571` — `save_my_data` replaces the **whole company blob**; the code comment at `:541` flags this as CRITICAL itself. No version/etag/optimistic lock on the owner save path.
- **Repro:** open the app on phone + laptop. Add an invoice on each. Whoever's 300ms-debounced save lands second **silently erases** the other's edits since load.
- **Fix:** add a `version` column, reject a save whose base version is stale (409 → client re-pulls & merges), or move to row-level writes. Non-trivial (architectural) — see P1.

### M3 — 💾 Cloud-save failures are silent ✅ Verified
- **Where:** `data.js:568-574` — `saveCloudNow` does `catch (e) { console.warn(…) }`. No toast, no retry queue, no "unsaved changes" indicator.
- **Impact:** `saveLocal()` runs first so data survives on *that device*, but if the cloud write keeps failing (expired token, network), edits live only in one browser's localStorage and never reach other devices — with no signal to the user. Pairs badly with M2.
- **Fix:** surface a persistent "not synced" indicator + retry-on-reconnect. ~3 h.

### M4 — 🔒 No phone verification + no signup rate-limit ✅ Verified
- **Where:** `signup.php` inserts an account directly; blocks duplicate phones but never verifies ownership (no OTP), and nothing throttles it.
- **Impact:** account squatting (register a competitor's phone) and automated spam-signups.
- **Fix:** SMS OTP before account creation + signup throttle. ~1 day (needs an SMS provider).

### M5 — 🤖 No per-account limit on AI extraction ✅ Verified
- **Where:** `extract.php` — each call is size-capped (60k text, 6MB/image, image-count cap: good), but **frequency is uncapped**.
- **Impact:** a compromised/leaked employee token can loop `/api/extract` and run up your Anthropic/Gemini bill.
- **Fix:** per-plant daily call cap or token-bucket. ~2 h. (Same root theme as H1: no rate-limiting layer anywhere.)

## 5. Performance / Scale

### P1 — 🐌 Entire dataset is one JSON blob ✅ Verified (architectural)
- **Where:** `app_data.data LONGTEXT`, one row per company; `data.js` loads and **rewrites the whole blob** on every change (`blob(true)` → `save_my_data`).
- **Impact:** grows unbounded with invoice history. Eventually hits `max_allowed_packet`, PHP memory, and slow saves; pagination is impossible on a blob. **Fine for a single lime factory's first few years; a hard ceiling after.**
- This is also the root of M2 (last-write-wins) and M3.
- **Fix (when it hurts):** migrate hot collections (sales, purchases, ledger) to real rows. Large effort — not needed now, but plan for it.

**Otherwise performant:** DB indexes are genuinely good (composite `(plant_id, company_id)` on every table, unique dedupe keys, purpose-built `idx_due`/`idx_poll`/`idx_stage`). Saves are debounced. Service-worker caches assets. The hot `data.php` path does **not** run `CREATE TABLE IF NOT EXISTS` (that's only login/signup/files).
